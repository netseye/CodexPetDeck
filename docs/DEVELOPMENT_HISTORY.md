# 开发与实验历史

本文保留项目从演示工程到当前稳定架构的关键决策，避免后续重复已经证伪的路线。

## 阶段 1：SwiftUI 控制台与 V2 连接

- 创建原生 macOS SwiftUI 工程。
- 实现串口发现、V2 帧编码/解码、CRC32、主题文件生成与上传。
- 修复初版“串口显示已连接但设备没有响应”的假连接：除 `FIND_DEVICE` 外必须发送 V2 `connect` JSON。
- 根据真机卡死复盘，固定 `FILE_START`/裸数据/`FILE_END`/Abort/Reload 时序。

## 阶段 2：Codex 状态与桌面控制

- 增量监听本机 Codex JSONL 会话，过滤内部 guardian/子任务。
- 维护最近六个用户可见会话，使用深链切换任务。
- 接入 token、额度、任务状态、工具事件和完成提醒。
- 逐步把审批、拒绝、快速模式、语音、滚动、停止、复制和项目目录对齐到 Codex Desktop。
- 权限检测改为真实事件监听结果；应用不能自动授予 macOS TCC 权限，只能打开设置引导用户。

## 阶段 3：主题与副屏

- 从最初空白副屏迭代到五行文本加额度进度条。
- 使用完整 428×142 可见区域，避免右侧留白。
- 20 个键使用独立图标和动作，旋钮使用六个互不冲突的 HID 组合。
- 完成任务后播放系统提示音并显示会话键完成动画；主题刷新加入防抖和文件通道串行化。

## 阶段 4：Codex Micro/Linux gadget 实验

为了研究是否可以让 MK20 直接枚举成 Codex Micro，曾进行以下实验：

- 为 MK20/T113 Linux 5.4.61 构建单 IN 端点的 ConfigFS HID function。
- 构建 ARM bridge，把原厂 KeyboardDevice 的 V2 PTY 流量复用到 HID 通道。
- 设计多代启动与恢复脚本，处理 UDC 绑定、端点不足、内核 ABI、前台进程所有权和掉线恢复。

这里的“编译 Linux”实际是针对设备内核版本编译一个外置模块，并不是重新编译或替换整个 Linux 系统。但部署 USB gadget 仍可能让串口暂时消失，存在设备需要物理重插或恢复脚本的风险。

最终结论：MK20 已经提供稳定的原厂 CDC + HID 双通道，生产功能无需模拟 Codex Micro。应用已回到原厂 USB 路径，实验代码只保留作研究记录。

## 阶段 5：硬件自检与 K18

- 增加 20 键、两枚旋钮各三种输入的 26 通道硬件自检。
- 分离旋钮与键格编码，并加入重复脉冲门控。
- 对下翻无反应进行逐层排查：业务动作、主题映射、原厂 HID、串口 `cmd=13`、JSON 和官方主题。
- 确认测试设备的物理 K18 没有稳定产生 `(3,2)`，而会落到 K17/K19 或出现底行多坐标。
- 原样复制官方 K18 Shift 动作仍未修复，进一步排除 CodexPetDeck 主题字段错误。
- 当前采用邻键和弦合并与低频功能降级，同时保留完整诊断记录。

## 当前基线

- 生产 USB：原厂 `1D6B:0104` CDC + `4250:426F` HID。
- 固件主要验证版本：MK20 V2.32；部分早期协议时序来自 V2.30 设备/样本。
- 应用身份：`com.screenkey.codexpetdeck.direct`。
- 不修改 Codex Desktop，不修改 MK20 启动脚本，不自动部署自定义内核模块。
- 已知未解决项：测试设备 K18 扫描异常，需要跨设备或设备侧矩阵日志进一步确认。
