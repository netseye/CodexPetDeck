# K18 排查记录

## 结论摘要

K18 是 4×5 网格中按行优先编号的第 18 个键，对应零起始坐标 `row=3, col=2`。当前测试设备没有稳定产生该坐标：同一个物理 K18 曾表现为 K17、K19，或短时间内同时出现相邻键。现有证据更符合设备固件矩阵扫描、消抖或物理行列线路异常，而不是 CodexPetDeck 把坐标映射错了。

这是单台设备上的观察，不能据此断言所有 MK20 或全部 V2.32 固件都存在同样问题。

## 已确认的标准映射

| 物理键 | 一起始编号 | 零起始坐标 | 当前 CodexPetDeck 功能 |
|---|---:|---|---|
| K17 | 17 | `(3,1)` | 上翻 |
| K18 | 18 | `(3,2)` | 项目目录 |
| K19 | 19 | `(3,3)` | 下翻 |

官方默认主题把 K18 配置为左 Shift。提取到的动作字段为：

```text
type      = keyboard
keycode   = 0x0200 (512)
keyString = "L Shift "
```

主题坐标和动作是两个不同层面：`row=3,col=2` 决定哪个物理格使用该动作，`keycode` 决定设备按下后发出什么 HID。改变 Shift 编码不能修复物理键被扫描成相邻坐标的问题。

## 已做实验

| 实验 | 观察 | 含义 |
|---|---|---|
| 使用自定义 4×5 主题给每个键独立动作 | 其他键可识别，K18 不稳定 | 不是缺少 K18 图标或主题项目 |
| 原样复用官方 K18 `controlData` | 仍未稳定成为 K18 | 不是字段顺序、Base64 或 Shift 文本差异 |
| 监听原厂 HID | K18 曾落到 K17/K19 | 异常在主机业务分发之前发生 |
| 监听串口 `cmd=13`/JSON 坐标 | 测试中没有稳定出现 `(3,2)` | 主机无法从正确坐标恢复该键 |
| 全通道自检 | 曾出现底行多个坐标脉冲 | 更像扫描/消抖/线路问题 |
| 与 MK20Control 交叉核对 | 其 20 键测试把 `(3,2)` 当普通键，没有 K18 特判 | 标准主机协议不要求特殊映射 |

普通 `keyboard` 动作由设备直接执行 HID，串口无事件是正常的。因此诊断坐标时应使用能够回传主机的动作或同时监听原始 HID，不能仅凭 `cmd=13` 沉默判断按键损坏。

## 当前软件缓解

- K18 放置低频“项目目录”动作，把常用“下翻”移动到已验证稳定的 K19。
- 主机短暂等待 K17/K19：若两者在去抖窗口内成对出现，则合并为一次逻辑 K18；单独出现仍执行各自动作。
- 对恢复得到的 K18 做二次去重，防止串口与 HID 同时触发。
- 硬件自检模式拦截真实 Codex 操作，便于安全收集 20 键覆盖率。

该缓解只针对已观察到的相邻键组合，并不能修复设备扫描本身。若其他设备没有异常，合并逻辑不会在单独按 K17 或 K19 时触发。

## 仍需完成的验证

1. 在另一台相同固件 MK20 上运行相同 20 键诊断主题。
2. 使用官方 ScreenKey 应用创建 K18 非键盘动作，确认官方主机看到的坐标。
3. 在设备侧采集按键矩阵扫描日志，分别观察按下、保持和释放。
4. 检查 K18 开关、二极管、排线和底行/第 3 列线路是否存在串扰或接触不良。
5. 若能获得不同固件，进行同一主题的 A/B 测试；不要在无可恢复镜像的情况下盲刷固件。

## 关于 MK20Control 的 Shift 差异

MK20Control 将“单独左 Shift”建模为标准 HID usage `0xE1`（225），组合键则把 modifier bitmask 放在高字节。官方默认主题样本使用的是 `0x0200`。可以把 `0xE1` 作为动作语义的兼容性测试，但该差异无法解释设备为什么从未稳定上报物理 `(3,2)`。
